# Правила разработки Goalissimo Backend

## Общий порядок работы

Основная ветка — `master`. Изменения вносятся через pull request
из отдельной рабочей ветки.

Один PR должен решать одну понятную задачу. Несвязанные изменения,
массовое форматирование и функциональные изменения следует разделять.

Перед слиянием PR проверяет второй участник команды.

## Рабочие ветки

Названия веток пишутся латиницей, в нижнем регистре.
Слова разделяются дефисами.

| Префикс     | Назначение                     | Пример                        |
|-------------|--------------------------------|-------------------------------|
| `feature/`  | Новая функциональность         | `feature/tournament-creation` |
| `fix/`      | Исправление ошибки             | `fix/token-validation`        |
| `hotfix/`   | Срочное исправление            | `hotfix/login-failure`        |
| `refactor/` | Переработка существующего кода | `refactor/team-registration`  |
| `docs/`     | Документация                   | `docs/api-description`        |
| `test/`     | Тесты                          | `test/tournament-service`     |
| `ci/`       | Автоматизация и CI             | `ci/pr-validation`            |
| `chore/`    | Сопровождение проекта          | `chore/update-dependencies`   |
| `release/`  | Подготовка выпуска             | `release/0.1.0`               |

Названия веток проверяются при ревью. CI автоматически проверяет название и описание самого PR.

## Название PR

Формат:

```text
тип(область): краткое описание
```

Область необязательна:

```text
ci: добавить проверку размера PR
```

Допустимые типы:

| Тип        | Назначение                                      |
|------------|-------------------------------------------------|
| `feat`     | Новая функциональность                          |
| `fix`      | Исправление ошибки, включая срочное исправление |
| `docs`     | Документация                                    |
| `style`    | Форматирование без изменения поведения          |
| `refactor` | Переработка без изменения внешнего поведения    |
| `perf`     | Улучшение производительности                    |
| `test`     | Добавление или исправление тестов               |
| `build`    | Система сборки и зависимости                    |
| `ci`       | Workflows и автоматизация                       |
| `chore`    | Остальные изменения сопровождения               |
| `revert`   | Откат изменения                                 |
| `release`  | Подготовка выпуска                              |

Тип пишется в нижнем регистре.

Область пишется латиницей в нижнем регистре; разрешены цифры и дефисы.
Примеры областей: `auth`, `tournaments`, `teams`, `database`.

Описание может быть на русском языке. Оно должно содержать
не менее 5 символов. Полное название PR — не более 100 символов.

Для несовместимого изменения допускается `!` перед двоеточием:

```text
feat(auth)!: изменить формат токена
```

Несовместимость и порядок перехода необходимо объяснить в описании PR.

Примеры:

```text
feat(tournaments): добавить создание турнира
fix(auth): исправить проверку токена
test(teams): проверить повторную регистрацию
release: подготовить версию 0.1.0
```

Префикс ветки и тип PR относятся к разным соглашениям:
например, ветка `feature/tournament-creation` имеет PR с типом `feat`,
а ветка `hotfix/login-failure` — PR с типом `fix`.

## Описание PR
Используется шаблон `.github/pull_request_template.md`.

Обязательные разделы, в указанном порядке:

1. `Что изменено` — конкретные изменения и поведение системы.
2. `Зачем` — решаемая проблема.
3. `Как проверено` — проверки, команды и результаты.
4. `Связанная задача` — ссылка на задачу либо «Нет отдельной задачи».

Заголовки второго уровня `##` нельзя переименовывать,
удалять или дополнять другими разделами этого уровня.
Для уточнений можно использовать списки и заголовки `###`.

Все разделы должны быть заполнены.

## Размер PR

Лимит: не более 1000 изменённых строк.

Размер считается как сумма добавленных и удалённых строк
по всем файлам PR. Учитываются код, тесты, документация,
конфигурация, сгенерированные и служебные текстовые файлы.

Крупную задачу следует разделять на несколько последовательных PR.
Каждый PR должен оставлять проект в рабочем состоянии.

Не следует уплотнять код в длинные строки ради обхода ограничения.

Двоичные файлы не оцениваются лимитом строк и проверяются при ревью.

## Локальные проверки

Используется Java 21 и Gradle Wrapper из репозитория.

Все проверки:

```bash
./gradlew check --continue
```

Проверки качества кода:

```bash
./gradlew checkstyleMain checkstyleTest pmdMain pmdTest --continue
```

Тесты и покрытие:

```bash
./gradlew test jacocoTestReport jacocoTestCoverageVerification
```

Порог покрытия основного кода по проекту в целом:

- строки — не менее 80%;
- инструкции — не менее 80%;
- ветви — не менее 80%, если они присутствуют.

Checkstyle и PMD проверяют основной код и код тестов.

Предупреждения Checkstyle также считаются нарушениями.

## Условия слияния

Перед слиянием должны пройти проверки:

- `PR format`;
- `PR size`;
- `Checkstyle and PMD`;
- `Tests and coverage >= 80%`.

Нужно одобрение второго участника команды.
После новых изменений ранее выданное одобрение должно быть обновлено.

Не следует сливать собственный PR без проверки другим участником,
отключать обязательные проверки ради слияния или отправлять
изменения напрямую в защищённую ветку `master`.
